# 分析策略

CLI schema、源证据和生成报告是字段及计数的权威来源。两个阶段分别验收，入口发现不以完整调用链分析成功为前提。

## 第一步：注册入口与业务归属

扫描源代码和配置中的路由、Webhook、消息/topic 绑定、定时/XXL-JOB 注册、事件订阅、导入/文件监视、CLI 命令、工作流触发和受支持的平台注册。仅扫描 controller 目录不能证明完整性。忽略缓存、构建、vendor 和生成目录；测试与非业务候选保留排除证据。

只有明确注册并承担业务用途的处理器才是业务入口。名称包含 Command、Listener 或 File 不构成注册证据。线程池提交、Lambda、内部异步执行、领域服务、DAO、出站客户端及普通辅助方法不独立计入入口；其业务动作在第二阶段保留。独立注册的消费、回调和恢复任务分别计数。健康检查、指标和静态资源只有明确非业务证据才能排除；Mock 也按实际业务用途判断。

将入口规范化为 `<trigger>:<package>.<declaring-class>#<method>(<parameter-types>)`；内部类包括所有外部类前缀，trigger 保留注册标识。`core_capabilities` 只保留全限定声明名，不能用裸 `doServe`、`doExecute` 或 `onMessage`。同一触发链的 Controller、Application 与模板方法不得重复计数；平台注册与模板声明指向同一源位置时合并。不同入口可共享辅助能力；能力冲突比较声明位置，不能比较调用方位置。

本阶段只检查注册、处理器身份、业务用途和归属所需的源码，不生成深调用链、分支或存储证据。无法支持的注册机制必须报告覆盖缺口。每个注册候选必须归入一个模块、证据充分地排除，或保留入口识别疑点；疑点只涉及触发、业务存在性、身份或归属。

## 业务模块和可见交付

优先按项目的一级业务域归组，一个业务域只对应一个 Markdown 文件。域内不同业务对象、职责、场景、渠道及触发方式都保留为入口章节，不因配置、创建、查询、回调、恢复等动作单独拆文件。域边界从项目术语、业务结果和用户分类取得，不内置固定业务词典。跨域入口唯一归属产生主要业务结果的域，其他域作为图中参与方，不能重复归属。域内链路差异必须保留，不因合并文件而合并不同业务规则。禁止按包名、Controller、触发类型或内部方法名拆分。

文件名列显示 `00-业务对象及核心职责概括`，不带 `.md`；实际文件加 `.md`，主体只含中文、字母和数字。使用自然的业务对象加核心职责、关系或生命周期名称，让读者从文件名大致知道主要内容；优先沿用项目已有业务文档的命名风格，仅提取风格，不能把某个项目的名称固化为通用词典。名称不强制添加“处理”“业务”“流程”等后缀，也不强制删除源码中本就有业务含义的词。长业务域用有意义的功能族概括，不堆全量功能动词、入口动作或 Swagger 分组。不能只写缺少对象和职责的缩写或短域名；“管理”只有在业务对象明确、确实概括维护职责时才可使用，不能泛化为“某某管理”。名称仍归属于同一个一级业务域，不按功能拆域。业务描述独立于文件名，优先参考 Swagger 的 @Tag.description 和 @Operation.summary/description，非 HTTP 入口参考源码注释及注册处理器说明，归纳具体业务对象和主要能力。同类列表、详情、分页及内部导出归并为查询能力，同对象的增删改归并为维护；开通、停用、订购、退订等不同业务含义的动作保留。允许使用分号、句号分段，不限制为一句话；不得用“负责 + 文件名摘要”代替业务说明，不逐接口罗列，不携带 client 标记或 HTML。共享 Controller 跨域时只描述本模块所属入口，不能引入其他域的能力，也不截断为“等业务”。文件名和描述负责概括，完整入口清单负责无遗漏，二者不能混为同一要求。缺少显式中文标签不是自动阻塞，可由注册与处理器证据推断，证据不足则标为待确认。

对话直接展示 CLI 完整三列表格：业务模块文件名、业务描述、入口数量；紧随排除类别、数量、原因，以及入口识别疑点数量和处理计划。总数或链接不能替代。模块映射、对话和 `业务流程覆盖总览.md` 必须一致。总览保留所有候选 ID、名称、触发、相对源码位置、范围状态和排除原因，可折叠但不得隐藏在机器数据中。各模块 Markdown 骨架保留业务范围、全部业务入口及分析状态，不写猜测流程或占位图。

必须对账：全部注册候选 = 已归属业务入口 + 已排除候选 + 待识别候选；已归属入口 = 总览业务入口 = 各模块清单入口，且每个入口恰好归属一个模块。排除的是独立入口身份，不能删掉第二阶段可达调用链中的操作。零入口只在完整扫描及排除证据充分时成立。

用户只确认业务模块分类一次，局部调整不影响其他归属。源码中可查事实先自行复核，不要求用户解释代码。既有会话授权优先；确认绑定 source/mapping fingerprint，源注册或归属变化后失效。

## 第二步：入口可达业务分析

从已确认入口追踪到业务结果，检查校验、状态保护、持久化、事务/锁、幂等、并发、缓存/文件、外部调用、消息生产、恢复和异步。线程池提交、执行和返回明确分开。只统计确认入口可达证据；非业务候选及无关源码问题不计入行为未决。共享链可以复用已核实证据，但各入口的入参、权限、分支和结果差异仍须独立核对。

只统计能传播至入口的活动异常，排除不可达或已捕获且不能逃逸的异常。异常被捕获不代表触发它的业务分支不可达；如果捕获后转换为认证失败等业务结果，触发条件和映射结果仍须出现在分支及图覆盖中。异常转换同时保留抛出和映射证据；动态错误码或未解析边界不得臆造。未知事实按入口记录：影响业务结果、状态、副作用或真实对象名称的疑点阻断该入口；不影响业务表达的内部细节如实报告，不机械升级为整体阻塞。

时序图用业务参与方和动作，不逐行翻译内部方法。每入口独立章节、`sequenceDiagram` 和 `autonumber`，真实分支使用 `alt/else`、`opt`、`loop`。矩阵包含条件、数据读取与比较、写入与副作用、响应结果，不加入源码函数依据列。可见业务正文不放源码路径和行号，也不新增独立源码证据章节；证据留在入口清单元数据、结构化结果、Mermaid 注释和外部 manifest。

持久化参与方保留真实资源名及中文业务标签：表、集合、KV 命名空间、索引、对象存储或文件分别按实际对象描述。无持久化动作不添加存储参与方。真实对象未知或业务标签没有依据时保留关键未决，不用“数据库”“资源”“业务对象”占位。

## 增量与完成报告

对比旧 Git 基线与当前目标，包含共享辅助器和配置；调用、分支、异常映射、状态、数据操作、事务/异步或共享依赖变化时重分析受影响入口。旧基线无法解析则完整扫描并报告比较不可用。未变入口保留 ID、归属、顺序及文档内容；删除入口同步移除清单/章节，新增入口重新确认归属。dirty 与 fingerprint 必须报告，不能只用 commit 声称源码一致。

报告 commit、dirty、模块/文档数、各触发类型数量、活动错误、新增/更新/删除入口、仅版本更新与业务变更文档、两阶段未决及覆盖。第一阶段成功不等于流程文档完成；第二阶段任一所需入口未完成不得报告整体成功。
